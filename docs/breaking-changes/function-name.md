> Это небольшое критическое изменение запрещает определять пользовательские функции, имена которых совпадают с именами обычных CSS-функций, имеющих специальный синтаксис, — даже если они написаны не в нижнем регистре. Также убирается специальная обработка парсинга для вызовов функций со специальным синтаксисом, когда в этом нет необходимости.

### Имена пользовательских функций {#user-defined-function-names}

Это изменение запрещает пользователям определять функции с именами `URL`, `EXPRESSION`, `ELEMENT` или с любыми комбинациями регистра этих же букв.

Полностью в нижнем регистре эти имена и раньше были запрещены. Однако имена функций в CSS чувствительны к регистру, поэтому для полной совместимости с CSS Sass вынужден применять специальные правила парсинга даже к вариантам в верхнем регистре. Из-за этого пользовательские функции не могут использовать эти имена — специальный парсинг должен происходить до того, как язык узнает, какие пользовательские функции вообще существуют.

!!! info "Информация"
    В рамках этого изменения были сняты некоторые другие ограничения на допустимые имена функций. Теперь функции с вендорными префиксами, имена которых заканчиваются на `-url`, `-expression`, `-and`, `-or` и `-not`, больше не будут вызывать ошибок.

### Вызовы функций {#function-calls}

Это изменение также уберёт специальный разбор для функции `expression()` или функций вида `progid:...()` с вендорными префиксами. Ни один браузер никогда фактически не реализовывал вендорно-префиксные версии этих функций, поэтому наличие специального разбора для них не нужно. Вендорно-префиксные функции `expression()`, например `-foo-expression()`, теперь будут парситься как обычные функции Sass, а вендорно-префиксные функции `progid:...()`, например `-foo-progid:bar()`, станут синтаксическими ошибками, потому что это в общем случае невалидный синтаксис CSS.

### Фаза 1 {#phase-1}

На данный момент Dart Sass выдаёт предупреждение об устаревшем коде, если вы определяете функцию с именем `URL`, `EXPRESSION` или `ELEMENT`, либо с теми же именами, но в любом сочетании заглавных и строчных букв. (Полностью строчные имена и раньше были запрещены и остаются запрещёнными.)

Вызовы функций с этими именами по-прежнему парсятся как обычные вызовы функций Sass: если существует пользовательская функция с таким именем — вызывается она, иначе происходит откат к обычной CSS-функции с нормальным разбором аргументов SassScript.

Dart Sass также выдаёт предупреждение об устаревшем коде для вызовов вендорно-префиксных функций `expression()`, но только в тех случаях, когда их поведение будет отличаться при разборе как обычных функций Sass. Сюда относятся вызовы, аргументы которых не являются синтаксически корректными выражениями SassScript, либо аргументы имеют особый смысл в SassScript, которого нет в обычном CSS. При этом вызовы, аргументы которых обрабатывались бы одинаково в обоих случаях, предупреждение не получают. Использование интерполяции всегда безопасно в обоих вариантах.

Dart Sass выдаёт предупреждение об устаревшем коде для **всех** вызовов вендорно-префиксных функций вида `progid:...()`.

## Можно ли отключить предупреждения? {#can-i-silence-the-warnings}

Sass предоставляет мощный набор опций для управления тем, какие предупреждения об устаревании вы видите и когда.

### Краткий и подробный режим {#terse-and-verbose-mode}

По умолчанию Sass работает в кратком режиме, где он будет выводить каждый тип предупреждения об устаревании только пять раз, прежде чем отключит дополнительные предупреждения. Это помогает гарантировать, что пользователи знают, когда им нужно быть в курсе предстоящего критического изменения, не создавая при этом огромного количества шума в консоли.

Если вы запустите Sass в подробном режиме, он будет выводить *каждое* предупреждение об устаревании, с которым столкнется. Это может быть полезно для отслеживания оставшейся работы, которую необходимо выполнить при исправлении устареваний. Вы можете включить подробный режим, используя [флаг `--verbose`](../cli/dart-sass/#verbose) в командной строке, или [опцию `verbose`](https://sass-lang.com/documentation/js-api/interfaces/Options/#verbose) в JavaScript API.

!!! tip "Совет"

    При запуске из [JS API](https://sass-lang.com/documentation/js-api/) Sass не делится никакой информацией между компиляциями, поэтому по умолчанию он будет выводить пять предупреждений для *каждой таблицы стилей*, которая компилируется. Однако вы можете это исправить, написав (или попросив автора плагина Sass вашего любимого фреймворка написать) [пользовательский `Logger`](https://sass-lang.com/documentation/js-api/interfaces/Logger-1/), который выводит только пять ошибок на каждое устаревание и может использоваться совместно для нескольких компиляций.

### Отключение устареваний в зависимостях {#silencing-deprecations-in-dependencies}

Иногда ваши зависимости имеют предупреждения об устаревании, с которыми вы ничего не можете поделать. Вы можете отключить предупреждения об устаревании из зависимостей, продолжая при этом выводить их для вашего приложения, используя [флаг `--quiet-deps`](../cli/dart-sass/#quiet-deps) в командной строке, или [опцию `quietDeps`](https://sass-lang.com/documentation/js-api/interfaces/Options/#quietDeps) в JavaScript API.

Для целей этого флага «зависимость» — это любая таблица стилей, которая не является просто серией относительных загрузок из входной таблицы стилей. Это означает всё, что поступает из пути загрузки, и большинство таблиц стилей, загруженных через пользовательские импортеры.

### Отключение конкретных устареваний {#silencing-specific-deprecations}

Если вы знаете, что одно конкретное устаревание не является для вас проблемой, вы можете отключить предупреждения для этого конкретного устаревания, используя [флаг `--silence-deprecation`](../cli/dart-sass/#silence-deprecation) в командной строке, или [опцию `silenceDeprecations`](https://sass-lang.com/documentation/js-api/interfaces/Options/#silenceDeprecations) в JavaScript API.

### Фаза 2 {#phase-2}

В одном из будущих релизов Dart Sass будет выдавать **ошибку** при определении пользовательских функций с именами `URL`, `EXPRESSION` или `ELEMENT`, а также при любом сочетании заглавных и строчных букв в этих именах. Вызовы функций с такими
именами будут парситься как [специальные функции](../syntax/special-functions), а не как обычные функции SassScript.

Вызовы вендорно-префиксных функций `expression()` будут обрабатываться как обычные вызовы функций SassScript, а вызовы вендорно-префиксных функций вида `progid:...()` будут приводить к ошибкам.
